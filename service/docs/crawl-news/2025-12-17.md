## Deliver secrets to Kubernetes pods without storing in etcd, using VSO

**ソース:** HashiCorp Blog

HashiCorp Vault Secrets Operator (VSO) のデフォルト機能では、Vault のシークレットを Kubernetes Secret オブジェクトに同期し、etcd に保存されます。しかし、Vault Enterprise の「保護されたシークレット」機能は、CSIドライバーを使用し、シークレットを Pod の起動時に動的にマウントするため、etcd に永続化されません。これにより、シークレットの露出期間が短縮され、セキュリティリスクが低減します。この機能は、規制の厳しい環境や高セキュリティ要件を持つ組織に適しており、etcd への依存を排除し、Pod 終了時にはシークレットも削除されます。

🔗 [記事を読む](https://www.hashicorp.com/blog/deliver-secrets-to-kubernetes-pods-without-storing-in-etcd-using-vso)

## Pricing Changes for GitHub Actions

**ソース:** Hacker News Best

GitHub Actionsの価格変更に関する記事は、2025年8月13日より、無料 tier の無料実行時間を大幅に削減し、GitHub Enterprise Cloud ユーザーへの無料実行時間を追加することを発表しています。

**主な変更点:**

*   **無料 tier の削減:** 無料 tier で利用できる GitHub Actions の無料実行時間が、月あたり 2,000 分から 3,000 分に削減されます。（公共リポジトリは 10,000 分）。
*   **Enterprise Cloud ユーザーへの追加:** GitHub Enterprise Cloud ユーザーには、月あたり 50,000 分の無料実行時間が追加されます。
*   **課金モデルの変更:** 実行時間に基づく課金モデルが導入されます。

**開発者にとっての重要事項:**

*   **無料 tier を超える利用:** 現在無料 tier を超えて GitHub Actions を利用している場合、追加料金が発生する可能性があります。
*   **Enterprise Cloud への移行:** GitHub Enterprise Cloud への移行を検討することで、無料実行時間を大幅に増やすことができます。
*   **コスト管理:** 変更点を理解し、アクションの実行時間を管理することが重要です。

この変更は、GitHub Actions の持続的な開発と改善のためのものです。

🔗 [記事を読む](https://resources.github.com/actions/2026-pricing-changes-for-github-actions/)

## 40 percent of fMRI signals do not correspond to actual brain activity

**ソース:** Hacker News Best

ミュンヘン工科大学（TUM）の研究によると、fMRI（機能的磁気共鳴画像法）で取得される信号の約40%は、実際の脳活動を反映していないことが明らかになりました。この原因は、脳の血管構造と局所的な血流の変動が、神経活動による信号と混同されることにあるとしています。

この発見は、fMRI研究における信号解釈の信頼性に疑問を投げかけるものであり、特に開発者にとっては、fMRIデータを分析する際に、この「ノイズ」を区別し、真の脳活動を正確に特定するためのより洗練されたアルゴリズムや解析手法の開発が求められます。従来の手法では見過ごされてきたこれらの非神経活動由来の信号を排除することで、より精度の高い脳機能マッピングや疾患診断への応用が期待されます。

🔗 [記事を読む](https://www.tum.de/en/news-and-events/all-news/press-releases/details/40-percent-of-mri-signals-do-not-correspond-to-actual-brain-activity)

## This is not the future

**ソース:** Hacker News Best

## 「This is not the future」記事要約

この記事「This is not the future」は、AI開発の現状について、過度な期待や誤解を指摘し、開発者が現実的な視点を持つことの重要性を説いています。

**技術的なポイント:**

*   **AIの「知能」への過信:** 現在のAIは、大量のデータからパターンを学習し、それに基づいて出力を生成する高度な統計モデルであり、真の理解や意識を持っているわけではないことを強調。
*   **「汎用人工知能（AGI）」との乖離:** 特定タスクに特化したAIは目覚ましい進歩を遂げているものの、人間のような汎用的な知能を持つAGIの実現には、まだ大きな技術的・概念的な課題が残されている。
*   **幻滅期（Trough of Disillusionment）の可能性:** 技術の過度な期待は、やがて現実とのギャップに苦しむ幻滅期を招く可能性がある。開発者は、AIの能力と限界を正確に理解し、現実的な目標設定と実装を進めるべき。

**開発者への重要情報:**

*   AIの「魔法」に頼るのではなく、その基盤となる技術、制約、そして潜在的なリスクを深く理解すること。
*   AIを単なる「ブラックボックス」として使うのではなく、その動作原理を理解し、責任ある開発を行うこと。
*   短期的な流行に踊らされず、長期的な視点でAI技術の進化と社会への影響を見極めること。

この記事は、AI開発者に対して、熱狂と現実のバランスを取り、地に足のついた開発を進めるための貴重な示唆を与えています。

🔗 [記事を読む](https://blog.mathieui.net/this-is-not-the-future.html)

## Novel Contributions of the Independent Variation Principle

**ソース:** Dev.to

Independent Variation Principle（IVP）は、変更の「ドライバー」ごとにドメイン知識を分割・統合する指針です。既存の原則と異なり、IVPは意思決定権限に基づく「パーティション特性」と「決定権限の根拠」を重視します。

主な貢献は以下の通りです：
1.  **パーティション特性**: 変更ドライバーがドメイン知識を互いに排他的かつ網羅的に分割すると定義。
2.  **決定権限の根拠**: 技術的基準ではなく、誰が変更を要求する権限を持つかで分離を決定。
3.  **双条件**: 要素は変更ドライバーを共有する**ならば**、モジュールを共有すると定義。
4.  **因果的凝集**: 構造ではなく、同じ理由で変化するかどうかで凝集を評価。
5.  **純粋性の離散性**: 1つのドライバーで純粋性1、2つで1/2となり、アーキテクチャ負荷が複利で増大。
6.  **必要・偶発的な不純物**: 複数のドライバーを持つモジュールでも、その必要性を区別。
7.  **知識からの要素導出**: ソフトウェア構造をドメイン構造に根ざす。
8.  **優先順位付けの6次元**: IVP違反の重要度を評価。
9.  **知識定理**: 知識整理とアーキテクチャ品質の形式的関連付け。
10. **既存原則の統合**: 他の設計原則がIVPのインスタンスであることを示す。

IVPは、なぜ特定の抽象化が機能するのか、いつ適用すべきかの統一的なフレームワークを提供します。

## Canonical JSON Model

**ソース:** Dev.to

Canonical JSON Modelは、AI実行状態を安定かつ決定論的に表現する標準フォーマットです。

**主な目的と利点:**

*   **決定論:** 常に同じ入力からバイト単位で同一のJSONを生成します。
*   **比較可能性:** 出力を比較、キャッシュ、diff、リプレイ可能にします。
*   **プロバイダー非依存:** プロバイダー固有の形式による非決定論の漏洩を防ぎます。
*   **信頼性:** キャッシュの信頼性向上、リプレイ、回帰テスト、監査を可能にします。

**実装ルール:**

*   フィールド順序は固定（`meta`, `system`, `tools`, `examples`, `history`, `user`, `assistant`, `output`）。
*   ネストされたオブジェクトはキーの辞書順でソートされます。
*   オプションフィールドは省略せず、明示的に`null`としてレンダリングされます。
*   数値や文字列のエンコーディングは安定しており、プロバイダーに依存しません。

Canonical JSONは、AIシステムの「コンパイル済み成果物」として扱われ、LLVM IRのようにプロバイダーに依存しない中間表現として機能します。これにより、プロバイダーの変更に強く、AIの挙動をテスト可能かつ信頼性の高いものにします。

## 【AWS / Terraform】ECS環境を完全閉域化するためにやったこと（ALB / ECR / Direct Connect / Route 53）

**ソース:** Qiita

本記事は、Terraformを用いてAWS ECS環境をパブリックアクセスから完全に隔離する「閉域化」を実現した際の具体的な手順を解説しています。

主な技術的ポイントは以下の通りです。

*   **ALB（Application Load Balancer）のプライベート設定**: ALBをプライベートサブネットに配置し、インターネットからの直接アクセスを遮断します。
*   **ECR（Elastic Container Registry）のプライベートエンドポイント**: ECRへのアクセスをVPCエンドポイント経由に限定し、インターネットを経由しないようにします。
*   **Direct Connectによるオンプレミス接続**: Direct Connectを利用して、オンプレミス環境とAWS VPCを専用線で接続します。
*   **Route 53によるDNS設定**: VPC内からのみECRなどのサービスに名前解決できるよう、Route 53のプライベートホストゾーンを設定します。

これらの設定をTerraformでコード化することで、セキュアなECS環境を効率的に構築する方法が示されています。エンタープライズ環境におけるセキュリティ要件を満たすための実践的なノウハウが詰まった記事です。
