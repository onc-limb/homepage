## v11.1.10

**ソース:** NestJS

NestJS v11.1.10がリリースされ、複数のバグ修正と機能強化が行われました。

**主な変更点:**

*   **コア:** 依存関係の注入（DI）におけるネストされたトランジェントプロバイダーのインスタンス化や、`resolve()` メソッドのプロバイダー解決に関するバグが修正されました。
*   **マイクロサービス:** gRPCストリームメソッドの戻り値型や、サーバーサイドのKeepAliveサポートが改善されました。
*   **共通モジュール:** `FileTypeValidator` のエラーハンドリングや、`fallbackToMimetype` の機能が強化され、`ValidationPipe` も改善されました。また、SSEハンドラーでPromiseがサポートされました。
*   **依存関係:** `express` や `@fastify/cors` などの依存パッケージが更新されました。

これらの変更は、NestJSアプリケーションの安定性、パフォーマンス、および開発者体験の向上に貢献します。

🔗 [記事を読む](https://github.com/nestjs/nest/releases/tag/v11.1.10)

## We removed 80% of our agent’s tools

**ソース:** Vercel Blog

Vercelは、社内開発していた複雑なtext-to-SQLエージェント「d0」のツールを80%削減し、ファイルシステム操作（bashコマンド実行）のみに限定したところ、性能が大幅に向上したと報告しています。

以前のエージェントは、専門ツールや複雑なプロンプトエンジニアリング、コンテキスト管理にもかかわらず、不安定で低速、メンテナンスも大変でした。しかし、bashコマンド実行という単一ツールに絞り、grep、cat、lsなどのコマンドをClaudeに直接使用させることで、エージェントはシンプルかつ強力になりました。

結果として、成功率100%、ステップ数・トークン数・応答速度の改善といった効果が得られ、「より少ないことで、より良くなる」という開発哲学を実証しました。これは、複雑なツールを排除し、基本的な機能に集中することの重要性を示唆しています。

🔗 [記事を読む](https://vercel.com/blog/we-removed-80-percent-of-our-agents-tools)

## Function start type now available in Runtime Logs

**ソース:** Vercel Blog

Vercelのランタイムログで、関数（Function）の起動タイプが確認できるようになりました。

これまで、関数がどのように起動したか（Hot、Warm、Cold）はログ上では明確ではありませんでした。しかし、今回のアップデートにより、リクエストごとの関数呼び出しにおいて、右側の詳細パネルで「Hot」「Warm」「Cold」のいずれかの起動タイプが表示されるようになります。

特に「Cold」スタートの場合、そのコールドスタートにかかった時間（例：「Cold (280ms)」）も合わせて表示されるため、パフォーマンスチューニングや問題特定に役立つ情報となります。この機能により、開発者は関数の起動パフォーマンスをより詳細に把握し、最適化を進めることが可能になります。

🔗 [記事を読む](https://vercel.com/changelog/function-start-type-now-available-in-runtime-logs)

## Infrastructure as demos: A Terraform-selling platform, built on Terraform

**ソース:** HashiCorp Blog

HashiCorpは、500人以上のソリューションエンジニア（SE）向けに、Terraformを活用したセルフサービス型のデモ環境プラットフォーム「Demos done right」（DDR）を開発しました。これにより、従来8〜10時間かかっていたデモ環境構築時間が10分未満に短縮され、月間800時間以上のSEの作業時間を節約。新規採用者のオンボーディング期間も3〜6ヶ月から30日に大幅短縮されました。

DDRは、HCP Terraformのプライベートレジストリに格納された標準化されたTerraformモジュールと、Sentinelによるポリシー・アズ・コードを組み合わせることで、ガバナンスを維持しつつ、SEが迅速かつ容易にデモ環境を構築・利用できる仕組みを実現しています。このプラットフォームは、デモ環境の提供だけでなく、HashiCorp製品の販売促進にも貢献し、1200万ドル以上の新規/更新契約、2000万ドル以上の総年間契約額（ACV）に影響を与えました。

この取り組みは、HashiCorpが自社製品（Terraform, Vault, Boundary）を活用して内部課題を解決した「ドッグフーディング」の好例であり、他社が同様のプラットフォームを構築する際の参考となるものです。

## LLMを大規模コードベースに適用するための課題と解決策

本記事は、大規模なコードベース全体を理解し、それに基づいてコード生成や分析を行うLLM（大規模言語モデル）の難しさと、その克服に向けたアプローチについて解説しています。

**技術的なポイント:**

*   **コンテキストウィンドウの限界:** LLMが一度に処理できる情報量（コンテキストウィンドウ）には限りがあり、大規模コードベース全体を一度に読み込むことができません。
*   **関連性の判断:** コードベース内のどの部分が現在作業している箇所に最も関連性が高いかをLLMが正確に判断することは困難です。
*   **意味論的な理解の不足:** コードの構文だけでなく、その意味論的な関係性や全体構造をLLMが深く理解する必要があります。

**開発者にとって重要な情報:**

*   **段階的な処理:** コードベースを小さなチャンクに分割し、関連性の高いチャンクをLLMに提供することで、コンテキストウィンドウの限界を回避します。
*   **検索拡張生成 (RAG):** コードベース全体を検索し、関連性の高い情報を抽出し、それをLLMのプロンプトに組み込むことで、より文脈に即した応答を生成します。
*   **ファインチューニング:** 特定のコードベースやドメインに特化したLLMをファインチューニングすることで、理解度と性能を向上させることができます。

**要約:**

大規模コードベースにおけるLLMの活用は、コンテキストウィンドウの限界や関連性判断の困難さといった課題に直面しています。記事では、人間による「Oversight and Guidance」を軸に、コードの段階的処理、RAG、ファインチューニングといった手法が、LLMを実用的なコード生成・分析ツールへと進化させる鍵であると論じています。開発者は、これらのアプローチを理解し、LLMとの協調作業を最適化することで、生産性向上に繋げることができます。

## 生成AIでテスト設計の手作業を半減させた話【Claude Code × Notion】

**要点:**

*   **課題:** QAエンジニアは、テスト観点表からテストケースへのコピペ作業やテストケース番号の採番ミスなど、単純作業に多くの時間を費やしていた。

*   **技術的ポイント:** Claude Codeのコード生成能力とNotionのAPI連携による自動化。
