## vCPUs are a marketing scam

**ソース:** Dev.to

vCPUは、クラウドプロバイダーがCPU時間を効率的に共有するための仕組みであり、必ずしも「詐欺」ではありません。多くのWebアプリケーションはCPUを継続的に必要とせず、リクエスト処理は短時間で完了し、その後アイドル状態になります。

そこで、プロバイダーは物理コアを専有させるのではなく、「CPUクォータ」という時間ベースの割り当てを提供します。これは、一定期間（例：100ms）ごとに利用できるCPU時間（例：25ms）を保証するものです。これにより、アイドル時間を有効活用し、リソースを共有します。

Linuxでは、CFS（Completely Fair Scheduler）の帯域幅コントローラーがこのクォータを管理しています。`cpu.cfs_quota_us`（利用可能時間）、`cpu.cfs_period_us`（期間）、`cpu.cfs_burst_us`（蓄積可能時間）といったパラメータで制御されます。

**開発者にとって重要なポイント：**

*   **vCPUは固定コア数ではない:** プロバイダーによって定義が異なり、共有インスタンスではCPU時間の一部を割り当てる「クォータベース」が一般的です。
*   **クォータ超過は「遅くなる」のではなく「停止する」:** クォータを超えた処理は、次の期間が開始されるまで一時停止されます。これにより、レイテンシが急増（P99レイテンシに影響）する可能性があります。
*   **バースト機能の理解:** 未使用のクォータは蓄積され、一時的なCPU需要の増加に対応できます。しかし、バースト残高がゼロになると、次の期間まで throttling（制限）が発生します。
*   **最適なリソースサイジング:** 平均CPU使用率ではなく、最も長い処理にかかるCPU時間を基準にサイジングすることが重要です。
*   **レイテンシへの影響:** クォータベースのモデルは、バースト処理には有効ですが、長時間同期処理を行う場合や、レイテンシに敏感なワークロードでは、 throttling による遅延に注意が必要です。

vCPUのクォータモデルを理解することで、リソースの無駄をなくし、レイテンシの急増を防ぐための適切なサイジングや設定が可能になります。

## Spring e Multithreading: Um pouco sobre como Beans Singleton lidam com múltiplas requisições

**ソース:** Dev.to

SpringフレームワークにおけるシングルトンBeanは、複数のHTTPリクエストを同時に処理する際に、同一インスタンスが複数のスレッドから安全に利用される仕組みを解説しています。

**要点:**

*   **シングルトンBean ≠ シングルスレッド:** シングルトンBeanは、Springコンテキスト内に1つのインスタンスしか存在しないことを意味しますが、複数のスレッドが同時にアクセスしても問題ありません。
*   **JVMのメモリ構造:** ヒープ領域（シングルトンBeanやコード、インスタンスフィールド）は共有されますが、スタック領域（ローカル変数、メソッド呼び出し）はスレッドごとに独立しています。
*   **Thread-Safeの秘訣:** コード（ヒープ）とローカルデータ（スタック）の分離により、スレッド間の競合が発生しません。
*   **ステートレス設計の重要性:** シングルトンBeanのインスタンスフィールドに可変状態を持たない（ステートレスにする）ことで、スレッドセーフティが自動的に保証されます。可変フィールドがあると、同期処理（synchronizedなど）が必要になります。

**結論:**

Spring Bootでは、シングルトンBeanをステートレスに設計すれば、リクエスト処理におけるスレッドセーフティはSpringが自動的に管理してくれるため、開発者はメモリ効率と並列処理性能を享受できます。

## How to Return HTTP 410 (Gone) Status in Next.js App Router: Two Workarounds

**ソース:** Dev.to

Next.js App Router では、HTTP 410 (Gone) ステータスコードを直接返す機能が現状ありません。この記事では、この制限に対する2つの回避策を紹介しています。

1.  **カスタムサーバー (Express.js) を使用する方法**:
    *   Next.js ページ内で `notFound()` を呼び出して 404 エラーを発生させます。
    *   Express.js サーバー側で、`app.render()` の前に `Object.defineProperty` を使用してレスポンスの `statusCode` プロパティのセッターをオーバーライドし、404 を 410 に書き換えます。

2.  **Next.js Middleware を使用する方法**:
    *   Middleware で API のレスポンスステータスを確認します。
    *   410 の場合、`NextResponse.rewrite` を使用して 410 ステータスでエラーページにリダイレクトします。
    *   この方法の欠点は、Middleware とページコンポーネントの両方で API を呼び出す必要があり、API コールが重複してしまうことです。

これらの回避策は、Next.js がカスタムステータスコードをネイティブサポートするまでの暫定的な解決策として役立ちます。

**要点:**

*   **エッジコンピューティングとは:** ユーザーに最も近いネットワークポイントで処理を実行すること。

    *   **低遅延:** リクエスト処理が速くなり、ユーザー体験が向上。

*   **具体例:** ユーザー登録フォームのデータ検証をエッジで事前に行うことで、バックエンドへの無効なデータ送信を防ぎ、処理を高速化。
*   **開発者への推奨:** TypeScript、クリーンコード、ミニマリズムを意識したコードをエッジで実行し、パフォーマンスと応答性に優れたアプリケーションを構築する。

エッジコンピューティングは、現代の分散型アプリケーション開発において、速度、スケーラビリティ、レジリエンスを向上させるための重要な進化であると強調しています。

## AWS初心者がAPI Gateway + Lambdaを映画館に例えてみた話

**ソース:** Qiita

AWSのAPI GatewayとLambdaの組み合わせは、Webアプリケーション開発において頻繁に利用される強力なコンビネーションです。この記事では、この二つのサービスを「映画館」に例えることで、その役割と連携を分かりやすく解説しています。

API Gatewayは、映画館の「受付」や「チケット売り場」に例えられます。外部からのリクエスト（映画を観たいという依頼）を受け付け、そのリクエストの内容（観たい映画、時間帯など）を判断します。そして、適切なバックエンドサービス（上映中の映画、座席情報など）へリクエストをルーティングする役割を担います。

一方、Lambdaは、映画館の「映写室」や「スタッフ」に例えられます。API Gatewayから渡されたリクエスト（「この映画を上映して」「この席に案内して」）を実行する、実際の処理を行う部分です。Lambda関数は、特定のイベント（リクエスト）が発生したときにだけ起動し、必要な処理（データの取得、加工、保存など）を実行します。

この二つを組み合わせることで、開発者は以下のようなメリットを享受できます。

*   **スケーラビリティ**: 映画館が混雑しても、受付や映写室を増やすように、API GatewayとLambdaは自動的にスケールアップします。
*   **サーバーレス**: 開発者はサーバーの管理に煩わされることなく、アプリケーションのロジック開発に集中できます。
*   **コスト効率**: Lambdaは実行時間に応じた課金なので、無駄なコストを削減できます。
*   **開発効率**: API Gatewayがリクエストのルーティングや認証などを担当するため、Lambda関数はビジネスロジックに特化できます。

つまり、API Gatewayは「リクエストの窓口」として、Lambdaは「実際の処理実行部」として機能し、この二つが連携することで、効率的でスケーラブルなサーバーレスアプリケーションを構築できるのです。
