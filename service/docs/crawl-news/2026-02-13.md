## Browserbase joins the Vercel Agent Marketplace

**ソース:** Vercel Blog

Vercelは、Vercel Agent MarketplaceにBrowserbaseが追加されたことを発表しました。これにより、開発者はインフラ管理なしで、AIエージェントにブラウザ自動化機能を提供できるようになります。

BrowserbaseはChrome DevTools Protocol (CDP) を介してリモートブラウザに接続し、ウェブサイトへのログイン、フォーム入力、動的ページの操作など、実際のウェブサイトと連携するワークフローを可能にします。

この統合により、開発者は単一のAPIキーでBrowserbaseを簡単にインストール・接続でき、請求の一元化やステートフルなセッションに対応したインフラの恩恵を受けられます。さらに、Vercel Sandbox AI Gatewayとの連携や、Vercelホストデプロイメントのブラウジングを中断させないWeb Bot Auth for Browserbaseのサポートも提供されます。

この機能により、ブラウザベースのエージェントワークフローの運用複雑性が軽減され、開発者はより効率的にAIエージェントを構築できるようになります。

🔗 [記事を読む](https://vercel.com/changelog/browserbase-joins-the-vercel-agent-marketplace)

## New deployments with vulnerable versions of the third-party package next-mdx-remote are now blocked by default

**ソース:** Vercel Blog

Vercelは、サードパーティ製パッケージ `next-mdx-remote` の脆弱性（CVE-2026-0969）を含む新しいデプロイメントをデフォルトでブロックするようになりました。これは、開発者のセキュリティを強化するための措置です。

この自動保護は、 `DANGEROUSLY_DEPLOY_VULNERABLE_CVE_2026_0969=1` という環境変数をVercelプロジェクトに設定することで無効化できますが、脆弱性のあるバージョンを使用することのリスクは高まります。Vercelを利用しているかどうかにかかわらず、パッチが適用されたバージョンへのアップグレードが強く推奨されます。

## 欧州大手決済処理業者がGoogle Workspaceユーザーにメール送信不可に

**要約:**

欧州の大手決済処理業者が、Google Workspaceを利用するユーザーへのメール送信ができなくなるという問題が発生しました。原因は、同社がGoogleのスパム対策基準を満たせず、Google側から送信元IPアドレスがブロックされたことと見られます。この問題は、決済業界におけるメール送信の重要性と、グローバルなメール送信におけるスパム対策の複雑さ、そしてIPレピュテーション管理の難しさを浮き彫りにしました。開発者は、自社サービスからのメール送信が滞らないよう、SPF、DKIM、DMARCなどの認証設定を適切に行い、IPレピュテーションを常に監視・管理することが重要です。

**技術的ポイント:**

*   **IPアドレスのブロック:** Googleのスパムフィルターにより、決済処理業者のIPアドレスがブロックされた。
*   **スパム対策基準:** Googleの定める厳格なスパム対策基準を満たせなかった。
*   **メール認証:** SPF、DKIM、DMARCなどの設定不備や、それらの設定と実際の送信状況との乖離が原因となりうる。
*   **IPレピュテーション:** 送信元IPアドレスの信頼度（レピュテーション）が低下した。

**開発者にとって重要な情報:**

*   グローバルなメール送信においては、各メールプロバイダーのスパム対策基準を理解し、準拠することが不可欠。
*   SPF、DKIM、DMARCの正確な設定と、それらを維持するための継続的な監視が重要。
*   IPレピュテーションの低下は、メール配信停止やビジネス機会の損失に直結するため、プロアクティブな管理が必要。
*   決済業界のように、メールによる通知や確認がビジネスの根幹をなすサービスでは、特にメール配信の安定性がクリティカル。

🔗 [記事を読む](https://atha.io/blog/2026-02-12-viva)

## lru_cache vs singleton in Python — they're not the same thing.

**ソース:** Dev.to

Pythonで@lru_cacheをシングルトンとして使うのは、手軽でコードも簡潔になりますが、本来の目的とは異なります。

**メリット**:
* **遅延初期化**: 必要な時にのみインスタンス化されるため、リソースを節約できます。
* **コードの簡潔性**: デコレーター一つで実装でき、冗長なコードが不要です。

**デメリット**:
* **初期化に時間がかかる場合**: 初回リクエストで遅延が発生し、パフォーマンスに影響が出る可能性があります。
* **スレッドセーフ性の誤解**: `@lru_cache`は内部状態の破損を防ぐだけで、インスタンスが一度だけ生成されることを保証しません。競合状態により、複数のインスタンスが生成されるリスクがあります。これは特に初期化に時間がかかる場合に顕著です。
* **マルチプロセッシングでの問題**: プロセスプールの作成など、ライフサイクル管理が重要な場面では、遅延初期化によるパフォーマンス低下や、意図しない複数インスタンス生成のリスクが高まります。また、終了処理（teardown）のフックもありません。

**結論**:

* **軽量でインスタンスが複数生成されても問題ないオブジェクト**には、`@lru_cache(maxsize=1)`の使用を推奨します。
* **ライフサイクル管理（厳密な初期化・終了処理）が必要なオブジェクト**には、従来のシングルトンパターンや、FastAPIなどのフレームワークが提供するライフサイクル管理機能の使用を推奨します。

「実用性は純粋さよりも優れる」という考え方もありますが、リスクを理解した上で使い分けることが重要です。

## Latência: O que é e como pode prejudicar uma aplicação

**ソース:** Dev.to

この記事は、ソフトウェアにおける「レイテンシ（遅延）」の定義、その悪影響、および測定・改善方法について解説しています。

レイテンシとは、HTTPリクエストやデータベースクエリの応答にかかる時間遅延のことです。この遅延が大きくなると、システム全体のパフォーマンス低下を招き、ユーザー離れや収益損失につながります。Amazonの調査では、レイテンシが100ms増加するごとに売上が1%低下する可能性があります。

レイテンシの影響を具体的に把握するため、著者は「ロングテールレイテンシ（Long Tail Latency）」という手法を提案しています。これは、システムで頻繁に実行されるクエリなどの応答時間を計測し、p50（中央値）、p75、p90、p99、p99.9といったパーセンタイル値で分析するものです。

例えば、p99ではシステム全体の1%の最も遅いクエリの応答時間を示し、極端な遅延を特定できます。この分析結果に基づき、キャッシュ実装、コードのリファクタリング、アーキテクチャの改善といった具体的な対策を講じることで、システムのパフォーマンス向上とユーザー満足度の向上を目指せます。

## いきなりAIエージェントでいい。でも“運用できる”とは別。業務改善〜市民開発〜AIエージェント化を「4つのゲート」で整理する最新版

**ソース:** Qiita

## AIエージェント導入を成功させる「4つのゲート」とは？

この記事は、「誰でもAIエージェントを作れる」という技術的可能性（Capability）と、現場で成果を出すための実現性（Viability）には大きな隔たりがあると指摘します。

AIエージェントを単に「作る」だけでなく、実際に「運用できる」状態にするためには、以下の「4つのゲート」を通過する必要があると提唱します。

1.  **業務改善ゲート:** AI導入の目的が明確で、業務課題解決に繋がるか。
2.  **市民開発ゲート:** 現場担当者がAIを開発・改善できるか。
3.  **AIエージェント化ゲート:** AIが自律的にタスクを実行できるか。
4.  **運用・ガバナンスゲート:** セキュリティ、コスト、倫理的側面を含めた運用体制が構築できるか。

開発者は、これらのゲートを意識し、技術的可能性だけでなく、運用・設計・ガバナンスまで含めた実現性の視点を持つことが、AIエージェント導入の成功に不可欠であると強調しています。

## なぜTypeScriptは成功しているのか。作者ヘイルスバーグ氏が語る7つの教訓

**ソース:** Publickey

TypeScriptの生みの親であるアンダース・ヘイルスバーグ氏が、その成功要因と開発で得た7つの教訓を語りました。記事では、特に以下の点が重要視されています。

1.  **JavaScriptとの後方互換性**: TypeScriptはJavaScriptのスーパーセットとして設計されており、既存のJavaScriptコードをそのまま利用できるため、開発者は段階的に導入できました。
2.  **型システムによる開発効率向上**: 静的型付けにより、コードの可読性、保守性、リファクタリングの容易さが向上し、大規模開発やチーム開発におけるバグの早期発見に貢献しています。
3.  **JavaScriptエコシステムとの連携**: npmなどのJavaScriptの豊富なエコシステムを活用できる設計が、TypeScriptの普及を後押ししました。
4.  **開発者体験の重視**: 優れたツール（IDEサポートなど）や、直感的で学習しやすい文法が、開発者の生産性向上につながりました。

これらの要素が、TypeScriptを今日のJavaScript開発におけるデファクトスタンダードへと押し上げた理由として挙げられています。
