## Server Components aren't SSR!

**ソース:** Dev.to

React Server Components (RSC) と Server-Side Rendering (SSR) は混同されがちですが、その役割と仕組みは根本的に異なります。SSRはサーバーで完全なHTMLを生成し、クライアントでのハイドレーションを経てインタラクティブにする一方、RSCはコンポーネントをサーバーでレンダリングし、その結果をJSON形式でクライアントに送ります。

これにより、RSCはクライアント側のJavaScriptバンドルサイズを大幅に削減し、Time To Interactive (TTI) を向上させます。データフェッチやビジネスロジックをサーバー側で実行できるため、ネットワーク負荷を軽減し、パフォーマンス最適化を図ります。RSCはインタラクティブな部分をクライアントコンポーネントに任せることで、両者の強みを活かす補完的な技術です。

🔗 [記事を読む](https://dev.to/devops-make-it-run/server-components-arent-ssr-4c32)

## The Secret Life of Go: Maps

**ソース:** Dev.to

Go言語のマップは、キーと値のペアを格納するデータ構造です。`make`関数またはマップリテラルで初期化する必要があり、未初期化のnilマップへの書き込みはパニックを引き起こします。

キーが存在しない場合、値のゼロ値（数値なら0、文字列なら""など）が返されるため、そのキーが実際にゼロなのか、マップに存在しないのかを区別するために `value, ok := myMap[key]` という「comma-okイディオム」を使用します。マップは`delete`で要素を削除でき、`range`でのイテレーション順序は意図的にランダムです。

マップは参照型であり、関数に渡すと元のマップが変更されます。キーには比較可能な型のみが使用でき、自動的にサイズを拡張します。この特性により、Goのマップは効率的で予測可能なデータ管理を可能にします。

🔗 [記事を読む](https://dev.to/aaron_rose_0787cc8b4775a0/the-secret-life-of-go-maps-4dma)

## Building a Frankenstein App in 14 Days: How Kiro Changed My Development Workflow

**ソース:** Dev.to

著者はKiro AI IDEを活用し、14日でOpenAPI解析、モックAPI、SDK生成を統合した「API Schema Explorer」を開発。従来の開発期間を大幅に短縮した。

成功の鍵は、Kiroの以下の3つの機能にある。

1.  **Steering Docs（ステアリングドキュメント）**: アーキテクチャや制約を記述した文書を全セッションに自動アタッチし、Kiroが常に一貫した文脈を理解。
2.  **Spec-driven development（仕様駆動開発）**: コード実装前にKiroに詳細なシステム設計「仕様」と「タスクファイル」を生成させ、予測可能な開発を実現。
3.  **Context continuity（コンテキスト継続性）**: 関連タスクを同じ会話スレッドで継続し、Kiroが過去の作業やコーディングスタイルを記憶、シームレスな統合と高品質なコード生成を可能にした。

これにより、開発ワークフローは「設計と構築」へと変革された。

## Swift 6.2、並行プログラミングを簡素化する、Approachable Concurrencyを導入

**ソース:** InfoQ Japan

Swift 6.2では、「Approachable Concurrency」が導入され、並行プログラミング開発の簡素化が図られます。

この機能により、Swiftコンパイラの動作がより予測可能になり、並行処理に関連するエラーや警告の数が大幅に減少します。特に、これまではコードの実際の問題と必ずしも関連しない、圧倒的な量のエラーや警告が発生する可能性がありましたが、それが解消される見込みです。開発者は不要な警告に煩わされることなく、コードの核心的な問題に集中しやすくなり、並行プログラミングの実装効率と開発体験が向上します。
