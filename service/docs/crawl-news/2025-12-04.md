## New npm package for automatic recovery of broken streaming markdown

**ソース:** Vercel Blog

Vercelが、ストリーミングMarkdownの破損を自動修復する新しいnpmパッケージ「Remend」をリリースしました。AIモデルがMarkdownをトークンごとにストリーミングする際、不完全な構文が生じレンダリングが崩れる問題がありますが、Remendはこの問題を解決します。

Remendは、 unterminated（未終端）なMarkdownブロックをインテリジェントに検出し、補完します。これにより、ストリーミング中でも安定した、整形された出力を保証します。コンテンツはストリームの進行に合わせてシームレスに更新され、ユーザー体験を向上させます。

このライブラリは、StreamdownのMarkdownレンダリングにも使用されており、本番環境のAIアプリケーションで実証済みです。false positiveを回避するインテリジェントなルールと、コードブロック内のアンダースコアやリンク内のネストされたブラケットといった複雑なエッジケースにも対応します。

開発者は、Streamdown経由で利用するか、`npm i remend`でスタンドアロンとしてインストールできます。AIアプリケーションなど、ストリーミングMarkdownを扱う開発者にとって、レンダリングの安定性を高める重要なツールとなります。

🔗 [記事を読む](https://vercel.com/changelog/new-npm-package-for-automatic-recovery-of-broken-streaming-markdown)

## Summary of CVE-2025-55182

**ソース:** Vercel Blog

CVE-2025-55182は、React Server Componentsにおける深刻な脆弱性（クリティカル）であり、React 19およびNext.jsなどの関連フレームワークに影響します。特定の条件で細工されたリクエストにより、意図しないリモートコード実行（RCE）の可能性があります。

**影響:**
React Server Componentsを使用するアプリケーションは、信頼できない入力を処理する際にRCEを許容する可能性があります。影響を受けるパッケージは `react-server-dom-parcel`、`react-server-dom-webpack`、`react-server-dom-turbopack` のバージョン19.0.0から19.2.0です。これらはNext.js (v14.3.0-canary.77以降、v15以降) やVite、Parcelなどのフレームワークやバンドラーに組み込まれています。

**解決策:**
React 19.0.1、19.1.2、19.2.1、およびNext.js 15.0.5以降など、修正済みのバージョンにアップグレードすることが強く推奨されます。Vercelは、WAFルールを更新し、ホストされている全プロジェクトを自動的に保護しました。

**その他:**
脆弱性はLachlan Davidson氏によって発見・報告され、Meta SecurityおよびReactチームとの協力により修正されました。WAF/CDNプロバイダーへの推奨事項も共有されています。

🔗 [記事を読む](https://vercel.com/changelog/cve-2025-55182)

## Zero trust for agentic systems: Managing non-human identities at scale

## More about Clean Architecture in Android. Example with Cross-cutting features.

**要約:**

この技術記事では、Androidアプリのクリーンアーキテクチャにおいて、例外処理やグローバルイベントなどのクロス・カッティング・フィチャーを効果的に実装する方法を説明しています。

**主なポイント:**

*   **グローバルイベントの単一障害点 (SSOT) の確立:** アプリ全体で共有されるグローバルイベントの発生源を一つにまとめます。

## Idempotent Dockerfiles: Desirable Ideal or Misplaced Objective?

**ソース:** Dev.to

Dockerfilesの「冪等性（Idempotency）」は、多くの場面で誤った目標であると指摘されています。実際には、チームが必要とするのは「レジストリに格納された不変で追跡可能な成果物」と、「セキュリティパッチや依存関係の更新を継続的に取り込む定期的なCI再ビルド」です。厳密な冪等性は、運用上の価値が低く、コストと複雑さを増大させるだけです。

重要なのは、ビルドプロセスを何度も実行して同じイメージを生成することではなく、ビルドされたイメージ（成果物）をレジストリに一意のハッシュ（ダイジェスト）で格納し、それをデプロイやロールバックに利用することです。これにより、常に最新のセキュリティパッチや依存関係を取り込みつつ、安定した運用が可能になります。

冪等性や再現性が真に求められるのは、厳格な規制、研究、高信頼性が要求される特殊なドメインに限られます。一般的なアプリケーション開発においては、不変な成果物の管理と継続的な更新こそが、より価値の高い目標となります。

🔗 [記事を読む](https://dev.to/dortort/idempotent-dockerfiles-desirable-ideal-or-misplaced-objective-e7c)
