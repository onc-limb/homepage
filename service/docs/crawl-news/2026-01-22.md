## 7.3.0

**ソース:** Prisma

Prisma 7.3.0 がリリースされました。今回のアップデートの目玉は、クライアント生成時のクエリコンパイラを「高速」または「軽量」なビルドから選択できる `compilerBuild` オプションの追加です。これにより、パフォーマンスとバイナリサイズのトレードオフを調整可能になりました。また、`$executeRaw` および `$queryRaw` でクエリコンパイラをバイパスできるようになり、パフォーマンスが向上しました。その他、MSSQL アダプターの更新、better-sqlite3 のバージョン固定、`@map` による enum の挙動の v6.19.0 への回帰、そして BigInt フィールドの JSON 集計における精度問題の修正（`::text` キャスト）が行われています。

🔗 [記事を読む](https://github.com/prisma/prisma/releases/tag/7.3.0)

## Is your TextMate 2 folding corrupt?

## TextMate 2の折りたたみ（Folding）が壊れた場合の対処法

TextMate 2でファイルを開いている際に、他のアプリケーション（例: Claude Code）がファイルを変更し、折りたたみマーカーが破損または誤った位置に配置される問題が発生することがあります。

この問題を解決するには、以下の手順を実行してください。

1.  **TextMate 2でファイルを閉じます。**
2.  **ターミナルを開きます。**
3.  **以下のコマンドを実行します:**
    ```bash
    xattr -d com.macromates.folded <ファイル名>
    ```
    （`<ファイル名>` の部分を実際のファイル名に置き換えてください）
4.  **TextMate 2でファイルを再度開きます。**

これにより、問題は解決され、折りたたみ機能が正常に動作するようになります。このコマンドは、TextMate 2がファイルに独自に付与している折りたたみ状態を示す拡張属性（xattr）を削除することで、状態をリセットします。

## [SC] Actor reentrancy

**ソース:** Dev.to

## [SC] Actor Reentrancy (再入可能性) に関する技術記事の要約

この技術記事は、SwiftのActorにおける「再入可能性（Reentrancy）」という問題について解説しています。Actor内の非同期関数（`async`）で`await`を使用すると、その関数は一時停止しますが、その間に別のタスクがActorにアクセスし、関数が再度実行される可能性があります。

**例:**
```swift
actor Counter {
  private var value = 0
  func count() {
    Task {
      value += 1
      try? await Task.sleep(for: .seconds(1))
      print("El contador va en \(value)")
    }
  }
}
```
この`Counter`actorの`count()`メソッドでは、`await`によって一時停止が発生します。複数の`count()`呼び出しが同時に行われると、`value`のインクリメントが順不同になり、最終的にすべてのタスクが同じ古い`value`を出力してしまう可能性があります。

これは「インターリービング（Interleaving）」と呼ばれる現象であり、非同期コードの実行中に発生します。Actorは一度に一つのタスクしか実行しませんが、`await`による一時停止中に他のタスクがActorにアクセスすることで、この問題が生じます。

**開発者にとっての重要性:**
この再入可能性は、状態の不整合や予期しないバグの原因となるため、開発者はActor内の非同期処理に注意を払う必要があります。特に、Actorの内部状態を変更するような処理で`await`を使用する場合は、再入可能性による影響を考慮した設計が求められます。

**要約:**
SwiftのActorでは、`async`関数内で`await`を使用すると、その関数が一時停止中に別のタスクがActorにアクセスし、関数が再度実行される「再入可能性」問題が発生します。これにより、Actorの内部状態が意図せず変更され、予期しない結果を招く可能性があります。開発者は、Actor内の非同期処理におけるこのインターリービング現象を理解し、状態の不整合を防ぐための注意深い設計が必要です。

## How to write more stable and testable code 👉 use encapsulation

**ソース:** Dev.to

OOPの原則であるカプセル化は、「状態を隠し、振る舞いを公開する」ことで、特にドメインロジックのテストにおいてコードの安定性とテスト容易性を向上させます。

カプセル化が不十分な場合、状態が直接操作され、オブジェクトの不変条件が破られる可能性があります。テストは「正しい使い方」を検証するだけで、ドメイン自体の正しさを保証しません。

一方、カプセル化を適用すると、オブジェクトは自身の状態をプライベートに保ち、操作を公開します。これにより、不正な操作は境界で拒否され、不正な状態の構築が不可能になります。

カプセル化により、テストはよりシンプルかつ意味のあるものとなり、リファクタリングの影響を受けにくく、不変条件が一貫して強制されるようになります。これは、単なる設計の綺麗さだけでなく、テストの信頼性を高め、ドメインの誤用を防ぐための重要な手法です。

## Operational Indistinguishability: A Technical Guide to the Doppelgänger Framework

**ソース:** Dev.to

「Doppelgänger」フレームワークは、正規の認証情報と許可された操作を用いてシステムを悪用する攻撃者を検出するための技術ガイドです。この攻撃は、通常のログでは異常が検出されず、攻撃者の意図のみが不正である点が特徴です。

記事では、この攻撃を「Identity Sampling（アイデンティティサンプリング）」、「Shape Acquisition（シェイプアクイジション）」、「Trust Embedding（トラストエンベディング）」、「Workflow Inheritance（ワークフローインヘリタンス）」、「Intent Substitution（インテントサブスティテューション）」という5つのフェーズで分析します。

従来のIOC（Indicators of Compromise）やシグネチャベースの検出では捉えられないため、攻撃者の行動パターン（シーケンス）や、個々のアイデンティティの「通常の振る舞いからの逸脱（Drift）」を監視することが重要だと述べています。

Doppelgänger攻撃を防ぐためには、以下の対策が推奨されています。
- **シーケンスを意識した分析:** 個々のイベントではなく、一連の行動パターンに注目する。
- **トラストグラフの可視化と監視:** 信頼関係の連鎖をマッピングし、不正な伝播を監視する。
- **機能マッピング:** ユーザーの通常行う操作と、実際に行っている操作を比較する。
- **アイデンティティごとのベースライン構築:** グローバルな平均ではなく、個々のユーザーの通常行動を基準とする。
- **JIT（Just-In-Time）アクセス:** 常に権限を持つのではなく、必要な時に必要な権限のみを付与する。
- **「Drift（逸脱）」をテレメトリとして扱う:** 一時的なはずの権限が永続化したり、サービスアカウントのアクセス範囲が拡大したりといった兆候に注意する。

SMB環境など、セキュリティ体制が手薄な環境ほど、Doppelgänger攻撃の標的になりやすいと指摘しています。開発者やセキュリティ担当者は、システムが「許可していること」と「本来意図されていること」のギャップを埋めるための、より高度な検出メカニズムを構築する必要があることを強調しています。

🔗 [記事を読む](https://dev.to/narnaiezzsshaa/operational-indistinguishability-a-technical-guide-to-the-doppelganger-framework-271b)
