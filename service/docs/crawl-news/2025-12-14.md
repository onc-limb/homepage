## v4.11.0

**ソース:** Hono Releases

Hono v4.11.0がリリースされました。

主な変更点は以下の通りです。

*   **型システムの改善**:
    *   ミドルウェアの型定義のバグを修正し、パスを持たないハンドラーでも正しく型付けされるようになりました。
    *   HonoクライアントでベースURLを型パラメータとして指定できるようになり、`$url()`メソッドがより正確なURL型を返すようになりました。これにより、SWRのようなライブラリで型安全なキーとしてURLを利用できます。
    *   `c.notFound()`の戻り値としてカスタムな`NotFoundResponse`型を定義できるようになり、404エラーレスポンスの型推論が向上しました。
*   **新機能**:
    *   Context Storageミドルウェアに`tryGetContext()`ヘルパーが追加され、コンテキストが存在しない場合にエラーではなく`undefined`を返すようになりました。
    *   Honoクライアントのクエリパラメータのシリアライズ方法を`buildSearchParams`オプションでカスタマイズできるようになりました。

これらの変更は、開発者の型安全性と柔軟性を向上させるものです。

## Coding Challenge Practice - Question 77

**ソース:** Dev.to

## 技術記事要約：コーディングチャレンジ練習 - 問題77

この記事では、配列中に一度だけ出現する整数を効率的に見つける問題とその解決策を紹介しています。

**技術的ポイント:**

この問題の鍵となるのは、**ビットごとの排他的論理和（XOR）演算子（^）**の特性です。XOR演算では、同じ値を2回演算すると結果は0になります（例: `a ^ a = 0`）。

**解決策:**

この特性を利用し、配列内の全ての要素に対してXOR演算を順番に適用します。ペアになっている整数は互いに打ち消し合い、最終的にXOR演算の結果として残るのは、一度だけ出現する整数のみとなります。

**コード例:**

```javascript
function findSingle(arr) {
  let result = 0;
  for (let num of arr) {
    result ^= num;
  }
  return result;
}
```

この簡潔なコードにより、O(n)の時間計算量で目的の整数を特定できます。開発者にとって、XOR演算の効率的な応用方法を学ぶ良い例となるでしょう。

## Why I Can't Use Java Records as JPA Entities

**ソース:** Dev.to

Java Recordsは不変なデータ保持クラスに便利ですが、JPAエンティティとしては利用できません。主な理由は、JPAがエンティティの状態変更（ミュータビリティ）と、プロキシによる遅延ロードを必要とするためです。Recordsは不変かつfinalクラスのため、これらのJPAの機能と互換性がありません。JPAエンティティには標準クラスとLombokの`@Getter`, `@Setter`などを組み合わせるのが推奨されます。RecordsはDTOなど、不変性が求められる用途に限定して使用すべきです。

## メモリの動的確保はなぜ嫌われるのか？

**ソース:** Qiita

メモリの動的確保は、プログラム実行中にメモリを割り当てる便利な手法ですが、特に組み込みやリアルタイムシステムでは敬遠される傾向があります。その理由は、**予測困難な実行時間**と**メモリ断片化**といった問題を引き起こすためです。

動的確保は、メモリ確保・解放のタイミングや所要時間が実行ごとに変動しやすく、リアルタイム性の保証が難しくなります。また、頻繁な確保・解放はメモリを断片化させ、最終的に十分な空きメモリがあっても連続した大きな領域を確保できなくなる可能性があります。これらの問題は、リソースが限られ、高い信頼性が求められるシステム開発において、致命的な欠点となり得ます。
