## 概要

AI エージェントによる自律開発ワークフローを収容するリポジトリ群。対象プロジェクトの GitHub issue を渡すと、タスク分解から実装・検証・敵対的レビュー・PR 作成・マージまでを人の張り付きなしで実行するエンジニアリングループ「extremis」と、プロダクトに必要な事項の洗い出しから issue 起票までを担うディスカバリーループ「veronica」からなる。

## 背景・課題

個人開発では、実装の手を動かす時間と「次に何をやるべきか」を考える時間の両方がボトルネックになる。LLM エージェントに開発サイクルの大部分を安全に委譲するために、実行系と発見系を分離した自律ワークフローとして構築した。

## アーキテクチャ

「veronica が『何を・なぜ』を決めて issue 化し、extremis が『どう作るか』を自律実装する」一方向のループ。対象プロジェクトはレジストリ（projects.toml）に一元登録し、各ワークフローの実行状態はプロジェクトごとに分離する。

### コンポーネント

#### extremis

自己改善エンジニアリングループ。issue の分解から実装・検証・敵対的レビュー・PR・マージまでを自律実行

- Elixir / OTP
- Rust（書き込み境界 sentinel）
- Claude Code
- GitHub CLI

#### veronica

マネジメント側ディスカバリーループ。観点カタログで必要事項を洗い出し、記述 → 敵対的検証 → Web 裏取りを経て issue を起票

- Python
- 観点カタログ（規約・監視・CI/CD・コスト等）

## 技術的な工夫

### Rust 製 sentinel による書き込み境界

エージェントの書き込みを Rust 製の sentinel で境界制御し、自律実行でも触ってよい範囲を技術的に保証。プロセスの信頼性が要る中核は Elixir/OTP、安全境界は Rust という役割分担にした。

### 敵対的検証をループに組み込む

実装後のレビューや、ディスカバリーで洗い出した項目の検証を「敵対的」なステップとしてワークフローに常設。生成物をそのまま信じず、反証を試みてから次工程に進める。

### ガードレール付き self-hosting

extremis は自分自身も改善対象にできる。ただし稼働中のチェックアウトを直接書き換えないよう、自己改善専用のクローンを分離し、人間のみが変更できる領域（sentinel）を確保した。

### 実行状態とプロジェクトの分離

対象プロジェクトを projects.toml に一元登録し、ワークフローの実行状態はプロジェクト別の dot ディレクトリに分離。ワークフロー同士は import せず自己完結させる規約で、追加・削除を容易にした。

## 課題と解決策

### 自律エージェントに任せる範囲の制御

**課題**: エージェントに実装からマージまで任せると、意図しない書き込みや自己破壊のリスクがある

**解決策**: Rust 製 sentinel による書き込み境界、自己改善専用クローンの分離、ユーザーの Go/No-Go 判断を挟む issue 起票フローという多層のガードレールで、自律性と安全性を両立させた。

### 初期実装からの言語移行

**課題**: extremis の初期 Python 実装では、長時間の自律実行に耐えるプロセス管理・耐障害性に限界があった

**解決策**: プロセス監視と耐障害性に強い Elixir/OTP へコアを再実装し、書き込み境界を Rust に切り出した。旧実装は凍結して段階的に廃止するマイルストーンを設けた。

## 成果・学び

- issue を投入してから PR マージまで人が張り付かずに完了する開発ループを実運用
- 発見（veronica）と実行（extremis）を分離した一方向ループというエージェント運用パターンの確立
- Elixir/OTP・Rust・Python を適材適所で使い分けるシステム設計の経験
